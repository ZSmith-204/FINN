# FINN CLI Layer — Integration Guide

**Audience:** the GUI layer (FINN Studio) and anyone scripting FINN.
**Companion spec:** [`reference.md`](reference.md) is authoritative for the config
format and generated-application semantics; this layer orchestrates it.
**Sibling layers:** [`database-layer.md`](database-layer.md) (data, below), [`api-layer.md`](api-layer.md) (HTTP, below), [`gui-layer.md`](gui-layer.md) (GUI, above).

This layer is the command-line interface (`finn_cli.py`) that ties the
`database` and `api` packages together into the end-user workflow:
**init → validate → build → run**. It owns the process model, the stdout/stderr
split, diagnostics, exit codes, the build manifest, and config discovery. It
**MUST NOT** re-derive schema DDL, type maps, validation, or codegen — those
belong to the `database` and `api` layers, which this layer calls directly.

The CLI is **standard-library only** for `init`/`build`/`validate`. Only `run`
imports `fastapi`/`uvicorn` (lazily) to serve the generated app, and those are
bundled into the frozen binary.

---

## 1. Running it

Three equivalent ways (from the repository root):

```bash
finn <command> ...              # the frozen binary (dist/finn)
python3 -m finn_cli <command> ...  # as a module
python3 finn_cli.py <command> ...  # as a script
```

Version and help:

```bash
finn --version            # finn 0.1.0
finn --version --json     # {"version": "0.1.0", "configSchema": 1}
finn --help
finn help build
```

## 2. Public surface (commands)

| Command | Purpose | Writes? |
|---|---|---|
| `finn init [TARGET_DIR]` | Scaffold a new `finn.json` from a template | the config |
| `finn validate [CONFIG]` | Parse + validate the config; print diagnostics | nothing |
| `finn build [CONFIG]` | Validate, then emit the `build/` directory | the build |
| `finn run [CONFIG]` | Build if stale, then serve the generated app | the build |

Flags per command:

```text
init     [TARGET_DIR] [--template example|minimal|blank] [--force] [--name NAME] [--json]
build    [CONFIG] [--config PATH] [--out DIR] [--quiet] [--json]
run      [CONFIG] [--config PATH] [--host HOST] [--port PORT] [--no-build] [--quiet] [--json]
validate [CONFIG] [--config PATH] [--json]
```

`init` templates: `example` (the full worked example, reference §11),
`minimal` (one table), `blank` (empty). `--name` writes `meta.name`.

`--json` switches a command's primary output to machine-readable JSON on
stdout; `run --json` emits NDJSON events (§7).

## 3. Config discovery & environment

Every file-taking command resolves the config in this precedence:

1. `--config PATH`
2. `$FINN_CONFIG`
3. `./finn.json`

Environment variables (v1 — no others):

| Variable | Meaning |
|---|---|
| `FINN_CONFIG` | Default config path (§ precedence) |
| `FINN_DB_PATH` | Overrides the DB filename/path, resolved relative to the build dir |
| `NO_COLOR`, `FINN_NO_COLOR` | Disable color output |

Color is emitted only when the target stream is a TTY and neither `NO_COLOR`
nor `FINN_NO_COLOR` is set.

## 4. The build pipeline

`finn build` runs these stages; the first `severity: "error"` diagnostic aborts
**before anything is written** (no partial output):

| Stage | Work | Layer called | Error |
|---|---|---|---|
| 0 | Locate config | — | `E0011` |
| 1 | Parse JSON | — | `E0012` |
| 2 | Structural validation | — | `E0021` |
| 3 | Semantic validation (FK targets, param resolution, DDL-in-endpoint) | `parse_database` + `parse_api` | `E0031` |
| 4 | Emit `main.py`, `API.py`, `DB.py` into `<out>` | `render_db_module` + `api.generate` | `E0041` |
| 5 | Create/verify SQLite DB at `<out>/<database.file>` | `database.bootstrap` | `E0041`, `E0042` |
| 6 | Write manifest `<out>/.finn-build.json` | — | `E0041` |
| 7 | Print summary | — | — |

`init` SQL runs only on first creation of the database (reference §4.6). A
config conflicting with the on-disk schema is `E0042` (exit 2) — a human must
resolve it; FINN has **no destructive bypass flags**. Generated files begin with
a `# generated by FINN — do not edit` header and are overwritten on every
build.

## 5. Diagnostics & exit codes

Every command reports problems through one diagnostic schema:

```json
{
  "severity": "error",
  "code": "FINN-E0031",
  "stage": "semantic",
  "path": "database.tables.orders.columns.user_id",
  "message": "...",
  "hint": null,
  "span": null
}
```

`path` uses the same JSON-path format as `database`'s `ConfigError.path`, so
the GUI and CI can consume both identically.

Error codes (`FINN-Exxx`): `E0011` config not found; `E0012` JSON parse error;
`E0021` structural; `E0031` semantic; `E0041` build I/O; `E0042` schema
conflict; `E0051` server failed to start (e.g. port in use); `E0061` `init`
target exists; `E0091` usage error. Warnings (never block, never change the
exit code): `W0002` declared `head`/`options` ignored; `W0003`
method/statement mismatch.

Exit codes:

| Code | Meaning |
|---|---|
| `0` | Success |
| `1` | Validation failure (a `severity: error` diagnostic) |
| `2` | I/O / runtime failure (path, port, schema conflict, init target exists) |
| `3` | Usage error (unknown command/flag) |
| `130` | Interrupted (SIGINT/SIGTERM mid-command) |

The `FINN-Exxx` code maps to the exit code as: `E0011`/`E0012`/`E0021`/`E0031`
→ `1`; `E0041`/`E0042`/`E0051`/`E0061` → `2`; `E0091` → `3`.

## 6. The build manifest

`<out>/.finn-build.json` records the CLI version, the config file's SHA-256,
the build timestamp, the artifact list, and whether the DB was newly created.
It is the staleness input for `run` (§7) and the artifact record the GUI reads.

## 7. Serving (`finn run`)

Staleness rule: read the manifest and rebuild if it is missing, if the config
SHA-256 differs, or if the CLI version changed; otherwise reuse the build.
`--no-build` skips the check (and errors with `E0041` if `build/` is missing).

Serving: the reference implementation serves the generated app **in-process**
via `uvicorn.Server` in a background thread, so the frozen binary needs no
third-party installs. The built app also remains runnable standalone
(`uvicorn build.main:app`) with no FINN runtime. `run` is a convenience wrapper.

`run --json` emits NDJSON events on stdout — `building`, `build_ok`,
`listening` (host/port/pid), `stopped` (exitCode), `error` (a diagnostic) —
while server logs go to stderr. SIGINT/SIGTERM shut down gracefully (exit `0`);
a port already in use is `E0051` (exit 2). There is **no hot reload** in v1:
edit the config, stop, then `run` again.

## 8. Gotchas

- **Owned files.** `main.py`, `API.py`, `DB.py`, and the manifest are
  FINN-owned and overwritten; user data lives only in `finn.json` and `finn.db`.
- **Stdlib-only, except `run`.** `init`/`build`/`validate` import nothing
  third-party; only `run` imports `fastapi`/`uvicorn` (bundled when frozen).
- **`init` dependency prompt.** In an interactive terminal (`stdin` +
  `stdout` both TTY), `init` offers to run `python -m pip install -r
  requirements.txt`; a declined or failed install never changes the exit code.
- **Frozen vs source.** When frozen, bundled data (`requirements.txt`) is read
  from `sys._MEIPASS`, and `init` suppresses the pip prompt (a frozen binary
  can't meaningfully mutate its own environment).
- **Coercion is split across the generated layers.** HTTP parameter coercion
  (§5.3 of the reference) lives in the generated `API.py`; write-side storage
  coercion and JSON serialization (§6.3) live in the generated `DB.py`.
  Neither is re-derived here.

## 9. End-to-end example

```bash
mkdir /tmp/demo && cd /tmp/demo
finn init                       # writes ./finn.json (example template)
finn validate                   # exits 0 when clean
finn build                      # emits ./build/{main.py,API.py,DB.py,finn.db}
finn run --port 8080            # serves; /healthz returns 200
# Ctrl+C to stop (exit 0)
```

The contract is pinned by `tests/test_cli.py` (stdlib `unittest`).
